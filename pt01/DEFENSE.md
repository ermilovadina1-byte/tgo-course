# pt01: запуск и разбор кода для защиты

В работе две самостоятельные части. Биграммная модель предсказывает следующее **целое слово** по предыдущему. BPE учится разбивать слова на повторяющиеся части. В pt01 биграмма не получает BPE-токены; сохраненные правила BPE понадобятся трансформеру в pt02.

## Запуск и файлы

Нужен Python 3.11+. Сам [run.py](run.py) использует только стандартную библиотеку. Команды из корня репозитория:

```bash
python pt01/run.py          # полный прогон: 1500 слияний
python pt01/run.py --fast   # быстрый прогон: 200 слияний
python -m pytest tests/test_pt01.py pt01/tests -q
```

Для последней команды нужен pytest: `python -m pip install pytest`. В настроенном окружении можно использовать `.venv/bin/python` вместо `python`.

Оба режима пишут в `pt01/artifacts/`: **быстрый запуск заменяет полный BPE версией на 200 слияний**. Для сдачи нужен результат полного запуска. Проверка сохраненных результатов через pytest их не перезаписывает.

Скрипт работает из любой папки, если указать путь к run.py. `HERE = Path(__file__).resolve().parent` находит папку самого скрипта, поэтому пути к корпусу и результатам не зависят от текущей папки терминала. При первом запуске `load_corpus` скачивает книгу, затем читает локальную копию. Временный файл заменяет основной после записи: прерванная загрузка не становится готовым корпусом.

| Файл в artifacts | Содержимое |
|---|---|
| bigram.json | Основные результаты биграммы, перплексии, генерация |
| bpe.json | Правила в порядке обучения, статистика, разбиения слов |
| corpus_stats.json | Числа слов и граница обучающей и проверочной частей |
| likelihood.json | Все 11 вероятностей исходного и перемешанного фрагментов |
| generation.json | Шесть образцов и настройки генерации |
| bigram_progress.json | Копия bigram.json для совместимости с предыдущими этапами |
| validation.json | Сохраненные результаты прежних проверок; текущий CI виден в GitHub Actions |

## Порядок выполнения

`main` разбирает флаг `--fast`, загружает текст, выделяет слова и делит их на две части. Затем считает статистику корпуса, вызывает `evaluate_bigrams`, сохраняет результаты и вызывает `evaluate_bpe`. Флаг меняет число слияний BPE; размер корпуса и проверочной выборки остается прежним.

Условие `if __name__ == "__main__"` запускает main только при выполнении файла. Когда тесты импортируют BigramModel, книга автоматически не скачивается и полный эксперимент не запускается.

## Слова и разделение корпуса

`tokenize_words` делает `lower().replace("ё", "е")`, затем применяет `[а-я]+(?:-[а-я]+)*`. Часть `[а-я]+` находит одну или несколько русских букв, а `(?:-[а-я]+)*` разрешает продолжения через дефис. «Ёлка, КОТ, кто-то!» превращается в `['елка', 'кот', 'кто-то']`, а «1-й» дает отдельное «й». Цифры, пунктуация и латинские слова отбрасываются. Границы предложений не сохраняются: соседними могут стать слова по разные стороны точки.

`split_words` вычисляет `len(words) * 9 // 10`. Для 433 082 слов граница равна 389 773: целочисленное деление округлило результат вниз. Последние 43 309 слов остаются для проверки. Если перемешать слова перед обучением, разрушится соседство, которое модель должна выучить.

Словарь биграммы содержит 45 309 разных обучающих слов и `<UNK>`, всего 45 310 вариантов. Число 48 117 в отчете относится к разным словам **всего корпуса**: это описательная статистика, словарь биграммы ею не расширяется.

## fit: какие счетчики нужны

Наш пример: `кот ест кот ест кот`.

`word_counts = Counter(words)` хранит частоты: «кот» встретился 3 раза, «ест» 2 раза. Counter возвращает 0 для отсутствующего ключа. `zip(words, words[1:])` соединяет каждый элемент со следующим:

```text
(кот, ест), (ест, кот), (кот, ест), (ест, кот)
```

`pair_counts` содержит две разные пары, каждая встретилась 2 раза. `context_counts = Counter(words[:-1])` считает слова, после которых было продолжение: «кот» 2 раза, «ест» 2 раза. Последний «кот» не имеет следующего слова, поэтому в знаменатель вероятности не входит.

`self.vocab = set(words) | {self.UNK}` добавляет к двум разным словам специальный вариант для неизвестных слов. Размер словаря в примере V = 3.

## prob: от счетчиков к вероятностям

При alpha = 1 вероятность «ест» после «кот»:

```text
P(ест | кот) = (число пар кот-ест + alpha) / (число контекстов кот + alpha * V)
             = (2 + 1) / (2 + 1 * 3) = 3/5 = 0.6
```

«Кот» и `<UNK>` получают по `(0 + 1) / 5 = 0.2`. Сумма равна 1. Добавка alpha в знаменателе умножена на V, потому что в числителях мы добавили ее каждому возможному продолжению.

Сглаживание дает ненулевую вероятность даже невиданной паре. Иначе одна такая пара обнулила бы вероятность всего проверяемого текста. На книге используется alpha = 0.01; единица здесь выбрана для ручного расчета.

Перед расчетом `prob` заменяет неизвестное предыдущее и неизвестное следующее слово на `<UNK>`. Если контекст неизвестен, его счетчик равен нулю и все варианты получают `alpha / (alpha * V) = 1/V`. Вероятность `<UNK>` относится к одному общему классу неизвестных слов.

## generate: как появляется текст

Метод начинает со списка `[start]`, затем `n_words - 1` раз берет последнее слово, считает вероятность каждого продолжения, применяет температуру и вызывает `rng.choices`. Это случайный выбор с весами: больший вес повышает шанс слова, но не делает его обязательным.

В примере отсортированный словарь равен `['<UNK>', 'ест', 'кот']`. При T = 1 его веса `[0.2, 0.6, 0.2]` можно представить отрезками на линии от 0 до 1: первые 20% отданы `<UNK>`, следующие 60% слову «ест», последние 20% слову «кот».

`random.Random(seed)` создает отдельный генератор случайных чисел, а сортировка словаря закрепляет порядок вариантов. При одинаковых данных, настройках и окружении seed позволяет воспроизвести выбор. Один seed не помог бы, если бы порядок множества set менялся между запусками.

Если всегда брать максимум, получится жадная генерация. На нашем примере она зациклится: «кот ест кот ест кот ест». В generate реализован случайный выбор.

## Температура

В `temperature_distribution` каждую вероятность возводим в степень `1/T`, затем делим значения на их сумму:

| T | `<UNK>` | ест | кот |
|---|---:|---:|---:|
| 0.5 | 9.09% | 81.82% | 9.09% |
| 1 | 20% | 60% | 20% |
| 2 | 26.79% | 46.41% | 26.79% |

При T = 0.5 получаем квадраты `[0.04, 0.36, 0.04]`, сумма 0.44; после деления на нее получается первая строка. Низкая температура усиливает преимущество лидера, высокая выравнивает вероятности. Само наиболее вероятное слово от этого не меняется.

Код считает ту же формулу через логарифмы:

```python
log_probs = [math.log(p) if p > 0 else -math.inf for p in probabilities]
maximum = max(log_probs)
weights = [math.exp((value - maximum) / temperature) for value in log_probs]
total = math.fsum(weights)
return [weight / total for weight in weights]
```

`exp(log(p) / T)` равно `p ** (1/T)`. Вычитание максимума вводит общий множитель, который сокращается при нормировке. Наибольший вес становится 1: это помогает избежать округления всех весов до нуля при очень маленькой температуре. `math.fsum` аккуратно суммирует числа с плавающей точкой.

T = 0 код отклоняет: деление на ноль недопустимо. Равномерное распределение после преобразования остается равномерным. Температура применяется при генерации и не участвует в подсчете перплексии в этой работе.

## logprob и perplexity

Для «кот ест кот» есть две правильные пары. В нашем примере при alpha = 1 каждая имеет вероятность 0.6:

```text
P = 0.6 * 0.6 = 0.36
log P = ln(0.6) + ln(0.6) = -1.021651...
PPL = exp(-log P / 2) = 1.666667...
```

Первый «кот» задан как контекст, его вероятность не вычисляется. Для N слов поэтому есть N - 1 проверок. `logprob` суммирует натуральные логарифмы вероятностей пар. Произведение множества маленьких вероятностей быстро округлилось бы до нуля; сумма логарифмов позволяет считать длинный текст.

`perplexity` меняет знак суммы, делит на число предсказаний и применяет exp. Это величина, обратная геометрическому среднему вероятностей правильных ответов. Чем больше вероятности настоящих продолжений, тем меньше перплексия. Если на каждом шаге правильное слово получало ровно 1/10, перплексия была бы 10. Это не доля ошибок и не число слов, которые модель буквально рассматривает.

`evaluate_bigrams` один раз обучает счетчики и меняет alpha между 1, 0.1 и 0.01. Каждый раз проверка идет на одном отложенном тексте. Получилось 15748.11, 7743.54 и 5309.64. Alpha = 0.01 лучше среди трех проверенных значений; это не доказательство оптимальности для любого корпуса.

Alpha меняет вероятности, рассчитанные из счетчиков, а температура преобразует готовое распределение для выбора слова. При большом alpha добавка `alpha * V` сильнее влияет на знаменатель. Особенно для редких контекстов распределение становится почти равномерным.

## Исходный и перемешанный фрагменты

`compare_likelihood` берет первые 12 проверочных слов, копирует список и перемешивает копию с seed = 42. Состав слов остается тем же, меняются соседние пары. Модель не дообучается на этом тексте.

Сравниваются суммы 11 логарифмов: -83.1429 у исходного порядка и -94.8913 у перемешанного. Число -83.1429 больше, поэтому исходный фрагмент вероятнее по модели. Это проверка одной перестановки одного фрагмента, а не доказательство, что биграмма всегда узнает связный текст.

В исходном фрагменте 5 пар не встречались в обучении. Сглаживание оставляет им положительную вероятность, поэтому логарифм конечен. В likelihood.json сохранены счетчики, вероятности и логарифмы каждой пары.

## BPE: обучение слияний

В `BPETokenizer.fit` поступает Counter слов **всего корпуса**, как требует задание. Частота от 5 ограничивает слова, участвующие в выборе слияний; для книги это 9002 разных слова. Алфавит собирается из всех слов, а итоговое разбиение применяется и к редким словам.

Каждое слово представляется кортежем букв и маркером `</w>`. Маркер сохраняет границу слова: токены `ма` и `ма</w>` различаются. Слияния выполняются внутри слов, через пробел они не переходят.

Допустим, «мама» встретилась 2 раза, «рама» 3 раза, «рамка» 1 раз. Для этого маленького примера установим min_frequency = 1. Пара «м а» встречается дважды в «мама» и один раз в «рама», ее частота равна `2 * 2 + 1 * 3 = 7`. Хранить каждое повторение слова отдельно не нужно: достаточно умножить число пар в слове на его частоту.

Первые пять правил нашего кода на таком наборе:

| Шаг | Пара | Новый токен | Частота перед слиянием |
|---|---|---|---:|
| 1 | м + а | ма | 7 |
| 2 | ма + `</w>` | `ма</w>` | 5 |
| 3 | р + а | ра | 4 |
| 4 | ра + `ма</w>` | `рама</w>` | 3 |
| 5 | ма + `ма</w>` | `мама</w>` | 2 |

После каждого шага пары считаются заново: предыдущие слияния изменили последовательности. `min(pair_counts, key=lambda pair: (-pair_counts[pair], pair))` выбирает максимальную частоту через отрицательное число. При равных частотах сравниваются сами пары лексикографически: результат не зависит от случайного порядка словаря.

`merge_pair` идет слева направо. Если текущий и следующий токены образуют выбранную пару, склеивает их и сдвигает индекс на 2; иначе переносит один токен и сдвигается на 1. В «ааааа» при слиянии «а а» получится `[аа, аа, а]`: один символ не участвует в двух заменах одновременно.

## BPE: применение к новому слову

`self.merges` хранит порядок обучения. `self.ranks` сопоставляет каждой паре ее номер: более раннее правило имеет меньший ранг. `encode_word` начинает с букв, находит разрешенные соседние пары и применяет пару с наименьшим рангом. Поиск повторяется, поскольку после слияния могли появиться новые допустимые пары.

После пяти правил из примера новое слово «рамам» обрабатывается так:

```text
[р, а, м, а, м, </w>]
[р, а, ма, м, </w>]   правило м + а
[ра, ма, м, </w>]     правило р + а
```

Больше подходящих правил нет. Частоты на новом слове не пересчитываются, самый длинный токен из словаря не ищется. Алгоритм следует сохраненному порядку правил. Соединение токенов и удаление конечного маркера восстанавливает исходное слово.

## Статистика BPE и связь с pt02

`evaluate_bpe` разбивает каждое различное слово один раз, затем умножает длину разбиения на частоту. Иначе частое «и» и редкое длинное слово имели бы одинаковый вес в средней длине, хотя в тексте встречаются по-разному.

```text
токенов на слово = 836977 / 433082 = 1.9326
символов на токен = 2245342 / 836977 = 2.6827
```

В числе токенов учитывается `</w>`, отдельный или вошедший в слитый токен. В числе исходных символов учитываются буквы и дефисы выделенных слов, но не пробелы и не маркер. Отношение 2.6827 описывает длину последовательности, не сжатие файла в байтах.

В полном режиме получились `['наполеон</w>']`, `['сказала</w>']` и `['не', 'удоволь', 'ствие</w>']`. Границы частых последовательностей могут отличаться от границ корней и окончаний. В сохраненной проверке быстрого режима было 3.1483 токена на слово; после 1500 слияний осталось 1.9326.

В pt02 список merges позволяет повторить то же разбиение. Затем токенам назначаются номера, и трансформер учится предсказывать следующий номер. В самой pt01 нет эмбеддингов, градиентов и обучения нейросети.

## Что уметь показать и изменить устно

| Просьба | Где искать и что объяснить |
|---|---|
| Посчитать вероятность | BigramModel.fit и prob: пары, контексты, V и alpha |
| Убрать сглаживание | Объяснить нулевые вероятности; alpha = 0 сейчас отклоняется конструктором |
| Изменить длину генерации | n_words у generate, стартовое слово входит в длину |
| Сделать жадную генерацию | Выбирать максимум вместо rng.choices; T = 0 не поддерживается |
| Изменить температуры | Список температур в evaluate_bigrams, затем получить новые образцы |
| Изменить число слияний | num_merges при вызове evaluate_bpe в main: штатно 200 и 1500 |
| Изменить частотный порог | min_frequency в вызове BPETokenizer.fit внутри evaluate_bpe |
| Обработать незнакомое слово | Биграмма заменяет на `<UNK>`, BPE применяет известные правила к символам |

Главные ограничения видны в результатах: биграмма забывает все, кроме предыдущего слова, поэтому длинный текст теряет смысл. BPE сокращает последовательность, но сам ничего не предсказывает и не понимает значения слов.
